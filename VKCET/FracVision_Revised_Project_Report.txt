ABSTRACT
FracVision is a modular research prototype for multimodal analysis of bone X-ray images. The
implementation combines image quality control and preprocessing with four model-oriented com-
ponents: RT-DETRv2 for fracture-related object detection, MedSAM for box-prompted segmen-
tation, DINOv2 for visual feature extraction, and a configurable multilabel classifier operating on
DINOv2 embeddings. A Mamba-style longitudinal model is also implemented for sequence-level
healing-stage classification when serial patient studies and appropriate labels are available. The
application is exposed through a FastAPI service and a Next.js web interface that supports single-
image analysis, serial comparison, and prediction history.
The verified codebase is intentionally conservative about medical claims. Every prediction carries a
non-clinical disclaimer, outputs include quality-control status and stage-level errors, and supervised
recovery-time training is disabled because the configured datasets do not provide verified time-
to-union or censoring labels. The repository contains model interfaces, adapters, training scripts,
evaluation utilities, tests, and deployment configuration, but the supplied snapshot contains no
dataset files or trained checkpoint artifacts. Accordingly, this report documents the implemented
architecture and algorithms without fabricating accuracy, latency, or clinical performance values.

1    Introduction

1.1 Background and project overview
Radiographic fracture analysis requires more than a binary image label. A usable analysis workflow
may need to check input quality, localize suspicious regions, create a pixel-level region estimate,
classify image-level attributes, and compare serial studies. FracVision implements these concerns
as a modular research system rather than as one monolithic predictor.
The repository identifies the system as FracVision, version 0.1.0. Its primary application path
is a browser-based Next.js interface communicating with a FastAPI backend. The backend loads
an inference pipeline during the application lifespan and maps model outputs into typed Pydantic
responses. A SQLAlchemy persistence layer stores de-identified prediction history. The model
package contains adapters for FracAtlas and GRAZPEDWRI-DX, preprocessing, pairing, training,
inference, and evaluation utilities.


1.2 Problem statement
The problem addressed is the engineering of a reproducible, multimodal X-ray analysis workflow
that can expose detection, segmentation, classification, and serial-comparison outputs through one
application interface while preserving uncertainty and safety information. The implementation
does not solve autonomous clinical diagnosis. It provides a research and integration foundation in
which each stage can fail independently and report its status.


1.3 Objectives
1. Standardize JPEG, PNG, and DICOM inputs through configurable quality-control preprocess-
   ing.
2. Detect fracture-related regions and return pixel-coordinate bounding boxes with confidence
   scores.
3. Use the highest-confidence fracture box as an optional MedSAM prompt for segmentation.
4. Extract DINOv2 visual features and produce multilabel probabilities through a classifier head.
5. Compare serial images using registration, embedding similarity, pixel differences, and mask
   overlap.
6. Provide longitudinal sequence modelling with a Mamba-style model while disabling unsup-
   ported recovery-time supervision.
7. Serve results through typed REST endpoints and present overlays, probabilities, warnings, and
   history in a web UI.


1.4 Scope and boundaries
The scope includes the implemented software, model interfaces, data adapters, configuration, API,
frontend, persistence, tests, and Docker deployment files. The supplied repository does not include
the configured datasets, trained checkpoint weights, measured evaluation reports, authentication,
or a clinical validation study. These absences are treated as explicit project boundaries.

3    Requirements Specification

3.1 Functional requirements
1. The service shall report readiness, load errors, model versions, and the mandatory clinical dis-
   claimer.

2. The service shall accept a single JPEG, PNG, or DICOM upload up to 50 MB at /api/predict.

3. The service shall return QC status, warnings, fracture status, confidence, detections, optional
   segmentation, optional classification, and stage errors.

4. The service shall accept prior and current images at /api/compare and return registration, em-
   bedding, pixel, and mask-comparison metrics.

5. The service shall persist and list recent upload predictions through /api/history.

6. The frontend shall provide analyze, compare, history, results, and about views.


3.2 Non-functional and safety requirements
The pipeline must degrade gracefully when a stage or checkpoint is unavailable. Inputs are writ-
ten to temporary files and removed after processing. The API rejects unsupported suffixes and
oversized files. Pydantic constrains confidence values to the interval [0,1]. The application explic-
itly labels outputs as not clinically validated and sets recovery\_training\_enabled=false. These

mechanisms are safety and validation features, not a substitute for authentication, authorization, or
clinical governance.


3.3 Dataset and checkpoint requirements
The configuration points to model/datasets/FracAtlas, model/datasets/GRAZPEDWRI-DX, and several
checkpoint paths. In the supplied snapshot these directories contain only .gitkeep; therefore no
dataset size, trained weight, or measured model result can be verified locally. The README and
frontend describe FracAtlas as 4,085 records and GRAZPEDWRI-DX as 20,328 records; those
figures are documented as project metadata, not as locally re-counted evidence.

5    Implementation and Algorithms

5.1 Image preprocessing and quality control
preprocess\_image accepts a path, bytes, or NumPy array. It decodes DICOM with pydicom when
the suffix is .dcm, otherwise uses Pillow. Grayscale input is converted to RGB-compatible output;
grayscale processing can apply CLAHE with a configured clip limit and tile grid. Images smaller
than the configured minimum dimension are rejected. The image is resized with aspect preserva-
tion and padded to a square target, configured as 1008 pixels in config.yaml. Optional mean/std
normalization returns a float tensor. Quality metadata records output dimensions, blur/exposure
statistics, warnings, and qc\_passed.


5.2 Detection algorithm
RTDETRv2Detector loads an RT-DETRv2 model when a checkpoint is available.     The configured
threshold is 0.30 and the maximum number of detections is 20. Detection results are converted

                                                     7
into labels, scores, and [xmin,ymin,xmax,ymax] boxes. Class mappings are derived from the config-
uration and dataset adapters; no new label vocabulary is introduced by the report. A placeholder
detector exists for missing model assets, so the presence of a class does not prove that trained
inference is available in the supplied snapshot.


5.3 Segmentation algorithm
For each image, the pipeline selects the highest-confidence detection whose label is fracture. That
box becomes the MedSAM spatial prompt. If a MedSAM checkpoint is loaded, the segmen-
tor returns a mask, score, and pixel area. If it is absent, the code returns an empty mask with
model\_loaded=false and a warning that the mask is a placeholder. Dice and IoU helpers are im-
plemented for supervised evaluation.


5.4 DINOv2 feature extraction and classification
The default DINOv2 variant is dinov2\_vits14, whose configured embedding dimension is 384.
The extractor returns the CLS token and patch tokens. The classifier maps the CLS embedding to
configured multilabel outputs. Its training helper implements focal loss with α = 0.25 and γ = 2.0,
and an optional temperature-scaling calibration module is present. At inference, probabilities are
returned as a label-to-probability dictionary, with predicted positive labels and a confidence value.

5.5 Serial comparison
SerialXrayComparator can register images with SimpleITK when available, compute DINOv2 em-
bedding cosine similarity, calculate pixel-level mean absolute difference and related image metrics,
and compare segmentation masks using Dice and IoU where masks are available. The API labels
these outputs as not clinically validated. This comparison path is distinct from the Mamba sequence
model: it compares two uploaded images directly, while the Mamba module consumes a prepared
sequence of per-visit features.


5.6 Longitudinal Mamba model
The Mamba input at each visit is the concatenation of DINOv2 features, detection features, segmen-
tation features, one time-delta scalar, and clinical features. An input projection maps this vector to

                                                  8
dmodel , followed by configurable Mamba blocks and a healing-stage head. The default configura-
tion uses dmodel = 256, dstate = 16, convolution width 4, expansion 2, and four layers. The imple-
mentation tries the CUDA mamba-ssm package and falls back to a pure-PyTorch selective-state-space
block. The output is per-timestep healing-stage logits plus the last valid sequence representation.


5.7 Recovery prediction boundary
The recovery module is explicitly a stub. is\_training\_enabled() always returns false because
neither configured dataset supplies verified time-to-union or censoring-status labels. Its forward
method returns a sentinel value and flags synthetic\_test\_only=true, clinical\_use=false, and
recovery\_training\_enabled=false. This is a deliberate implementation safeguard, not a recovery-
time prediction result.


5.8 Dataset adapters and preprocessing data flow
The FracAtlas adapter reads dataset.csv, COCO polygon masks, YOLO text boxes, Pascal VOC
boxes, and fractured/non-fractured image directories. It uses image identity as a surrogate patient
identifier because no separate patient ID is provided. The GRAZPEDWRI-DX adapter reads CSV
metadata, extracts images from folder\_structure.zip when required, parses Pascal VOC boxes,
and groups true patient sequences by numeric patient ID and timehash. Both adapters explicitly
mark recovery labels as unavailable. Split creation is patient-aware where the adapter provides pa-
tient identity, and pair construction creates ordered consecutive studies for longitudinal processing.

7    Results and Discussion

7.1 Implementation results
The verified result is an integrated application skeleton with a complete request-to-result path, typed
API contracts, persistence, model wrappers, dataset adapters, training/evaluation entry points, fron-
tend views, Docker files, and automated tests. The project demonstrates architectural integration
rather than a completed clinical model validation campaign.


7.2 Testing evidence
The repository contains unit tests for adapters, preprocessing, model output shapes, loss behavior,
mask metrics, and recovery flags, plus integration tests for health, invalid file types, and upload
size limits. Dataset-dependent tests skip when local datasets are absent. Model initialization tests
can also skip when weights or network access are unavailable. This behavior is appropriate for a
repository that does not commit large data or checkpoint assets.


7.3 Limitations and observations
The principal limitations are the absence of local datasets/checkpoints, disabled recovery-time su-
pervision, research-only disclaimers, and lack of an authentication/authorization layer in the in-
spected code. The frontend includes illustrative content and interface copy, but only backend route
and model code was treated as evidence for technical capability. A future release should add re-
producible dataset manifests, checkpoint hashes, experiment outputs, model calibration reports,
privacy controls, and clinical validation governance.


8    Feasibility Study

8.1 Technical feasibility
The modular Python architecture supports CPU fallback for the Mamba block and configurable
CUDA execution for available models. Docker Compose separates CPU and GPU profiles. The
API and frontend boundaries are conventional and testable. The major technical risk is the compute
and storage cost of foundation models and medical-image datasets.




                                                 10
8.2 Economic and operational feasibility
The software stack is based primarily on open-source frameworks, but practical operation may
require GPU infrastructure and licensed/approved clinical data access. Operational deployment
requires clinician review, secure data handling, access control, monitoring, and validation beyond
the current research prototype.


9     Conclusion and Future Scope
FracVision implements a coherent multimodal X-ray analysis platform in which preprocessing, de-
tection, segmentation, feature extraction, classification, comparison, longitudinal modelling, API
serving, web visualization, and persistence are connected through explicit interfaces. Its strongest
engineering characteristic is transparent degradation: unavailable stages produce warnings and
flags rather than being presented as clinically reliable results. The repository also correctly pre-
vents unsupported recovery-time training.
Future work should supply versioned datasets and checkpoints, run the existing training/evaluation
scripts, publish reproducible metrics, integrate real model monitoring, implement authentication
and audit controls, harden DICOM privacy handling, and perform independent clinical validation.
Recovery-time prediction should remain disabled until verified time-to-union and censoring labels
are collected under an approved clinical protocol.
